### PERF-1　每次按键整页重绘，且无防抖 —— P0

**问题描述**
`render()`（`src/report.py:4884`）做的是 `document.getElementById('content').innerHTML = fns[TAB]()`，
即**整块内容区撕掉重建**。两个搜索框直接挂在它上面：

```js
// :2608  setMailQ —— 每敲一键 render() 一次
function setMailQ(v){
  MAILQ = (v || '').trim();
  MAILPAGE = 0;
  render();
  const box = document.getElementById('mailq');
  if (box){ box.focus(); box.setSelectionRange(box.value.length, box.value.length); }
}

// :4123  物料码搜索 —— 同样每键 render()
'onclick... oninput="CODEQ=this.value;render()" '
```

对照之下，Ship-To 网格**是**防抖 + 服务端分页的（`:3544` `let SHIPT = null; // search debounce timer`、
`SHIPLIMIT = 100`），两套做法并存。

**优化方向**
1. 给两个搜索框加防抖（150–200ms），照抄 `SHIPT` 的写法即可；
2. 进一步：搜索时只重绘表格区，不动整块 `#content`。给表格容器一个 `id`，
   `renderCodes`/`renderToday` 拆成「骨架」+「表格体」两个函数，输入时只换表格体。

```js
let MAILT = null;
function setMailQ(v){
  MAILQ = (v || '').trim();
  MAILPAGE = 0;
  clearTimeout(MAILT);
  MAILT = setTimeout(() => {
    const body = document.getElementById('mailbody');
    if (body) body.innerHTML = poTable();      // 局部更新，输入框不动
    else render();
  }, 180);
}
```

**预期收益**：长列表下每次按键从「重排整页 + 重建全部 DOM + 重挂 tooltip」
降到「只换一个 tbody」。Inbox 有几百行时手感差异明显；同时**顺手消灭 PERF-2 的丢焦点问题**。

### PERF-2　物料码搜索框每敲一键丢焦点（真 bug）—— P0

**问题描述**
`report.py:4123` 的搜索框绑 `oninput="CODEQ=this.value;render()"`，
`render()` 会把 `#content` 整块 `innerHTML` 替换 —— 输入框作为旧节点被销毁，
焦点回到 `body`。**第二个字符开始就打不进去了。**

`setMailQ`（`:2608-2614`）对此有补救（`box.focus(); box.setSelectionRange(...)`），
但 `CODEQ` 这条路径**没有**任何焦点恢复。这是个用户可直接感知的功能缺陷。

**优化方向**
最小修复：照抄 `setMailQ` 的焦点恢复。但根治是 PERF-1 的局部更新 ——
输入框不再被销毁，焦点天然保留，那两行 hack 也可以删掉。

```js
// 最小修复（若暂时不做局部更新）
oninput="CODEQ=this.value;render();
         const b=this;requestAnimationFrame(()=>{b.focus();
         b.setSelectionRange(b.value.length,b.value.length);})"
```
注意：属性内联写 `const` 在部分内联 handler 作用域下会有问题，
建议改成命名函数 `setCodeQ(v)`，与 `setMailQ` 对称。

**预期收益**：物料码页搜索从"只能搜一个字母"变成可用。改动量极小。

### PERF-3　`/api/dashboard` 载荷过重，且全量重拉 —— P1

**问题描述**
`of_core.py:359 dashboard_data()` 一次返回 **6 个列表**，其中 5 个无 LIMIT：
`today`、`unclassified`、`duplicates`、`unprocessed`、`excluded` 都是
`SELECT *`；只有 `history` 有 `LIMIT 2000`（`:375`）。
`_rows()`（`:341-354`）还给每行做 3 次 `json.loads`
（`attachments` / `pdf_paths` / `att_states`）再算 `att_docs`。

前端 `load()`（`:1535`）和 `pollDuringSync()`（`:1551`）都是**整包重拉**，
后者在采集期间每 3 秒一次。也就是说：同步跑 5 分钟 = 100 次
「全表 SELECT * + 逐行 JSON 解析 + 整包 JSON 序列化」。

**优化方向**
1. **只传需要的列**：列表页实际用到的无非 `id / received_at / sender /
   sender_domain / subject / customer / po_number / status / att_docs / erp_file /
   att_seq` 等，不必把 `attachments`/`pdf_paths`/`note` 全发到浏览器。
   加一个 `select_columns` 版 `_rows_light()`。
2. **给所有列表加 LIMIT**，跟 `history` 一致（`LIMIT 2000` 已是先例）；
   真要看更老的走 Reports 页的服务端聚合。
3. **`pollDuringSync` 只拉增量**：新增 `GET /api/sync_state` 已经有了，
   让它带上 `found/new`，仅当 `new` 变化时才 `load()`，而不是定时整包拉。

**预期收益**：同步期间的 CPU/IO 明显下降；历史累积到上万封后，
dashboard 接口不会随数据量线性变慢。也顺带减少主线程 JSON.parse 时间。

### PERF-4　1MB 主数据每次读都重新 `json.load` —— P1

**问题描述**
`_read_json`（`of_master.py:214`）每次调用都 `open + json.load`，
`mm_load`（`:272`）、`load`（`:1807`）、`dm_load`（`:2275`）都走它。
`material_master.json` 约 1MB、`ship_to_master.json` 约 2.8MB。

有意思的是，**同一文件里已经有两套 mtime 缓存**了：
`_STATE_CACHE`（`:1882`，注释写明"called on every dashboard render"）
和 `_DM_CACHE`（`:2385`，注释甚至记录了不缓存时"the whole dashboard crawled"）。
`mm_load` 却没享受同等待遇。

**优化方向**
把 `_STATE_CACHE`/`_DM_CACHE` 的 `(mtime_ns, size)` 键抽成通用的
`cached_json(path)`，三处共用：

```python
_JSON_CACHE = {}   # path -> (key, data)

def cached_json(path, default):
    key = _stat_key(path)
    hit = _JSON_CACHE.get(path)
    if hit and hit[0] == key:
        return hit[1]
    data = _read_json(path, default)
    _JSON_CACHE[path] = (key, data)
    return data
```
注意写路径（`mm_save`/`save`/`dm_save`）要同步失效或直接回填缓存，
否则"改完主数据界面不刷新"会成为新 bug —— `_write_json` 里 `os.replace`
之后顺手 `_JSON_CACHE[path] = (_stat_key(path), data)` 即可。

**预期收益**：`/api/codes`、下拉构造、分类器路径上的 3.8MB JSON 解析
从"每次调用"降到"文件变了才解析"。改动集中在 3 个函数，风险低。

## 二、交互体验

### UX-1　56 处 `alert()` 作为主要反馈手段 —— P1

**问题描述**
`report.py` 里 `alert(` 出现 **56 次**，覆盖错误、成功、信息三类。
浏览器 alert 是**阻塞模态**：不能样式化、不能堆叠、不能自动消失，
打断操作流。而项目里**已经有** `toast(msg, sticky)`（`:4655` 附近）
和 `runWithProgress()` 两套更好的反馈通道，用在同步/读取上。

典型冲突：
```js
// :1675  Confirm 成功后 —— 用 alert 说成功
if (r.message) alert(r.message);
// :1713  生成文件成功后 —— 又是 alert
if (r.message) alert(r.message);
```
成功类反馈完全不该用模态框。

**优化方向**
分级反馈：
- **成功/提示** → `toast(msg)`（2s 自动消失）
- **进行中** → `toast(msg, sticky)` 或 `runWithProgress`（已有）
- **可恢复的错误** → toast + 行内错误条（预览卡里已有 `warnings` 数组的样式基础）
- **不可恢复 / 需要用户决策** → 保留对话框，但改成应用内确认卡（预览卡的
  `confirmPreview()` 模式已经在用）

建议先做一次**纯分类**：把 56 处按「成功 / 错误 / 确认」打标，再分批替换。
成功类（约 1/3）改动是机械替换，一次 PR 就能做完。

**预期收益**：操作流不再被弹窗打断；完成一条 PO 的点击/弹窗次数明显下降。
这是**整体手感**提升最大的一项。

### UX-4　`api()` 无错误处理，网络故障时界面无解释 —— P1

**问题描述**
```js
// report.py:1073
async function api(path, body){
  const r = await fetch(path, body ? {...} : {});
  return r.json();
}
```
三个缺陷：
1. `fetch` 抛异常（服务没起、端口挪位）→ 调用方拿到 rejected promise，
   多数调用点只有 `const r = await api(...)` 没有 try/catch → **静默失败**；
2. 服务端 500 返回 JSON，但 `r.ok` 没人检查，`r.error` 只在部分调用点被看；
3. 没有超时，Outlook 卡住时按钮永久"没反应"。

**优化方向**
```js
async function api(path, body){
  const ctl = new AbortController();
  const t = setTimeout(() => ctl.abort(), 60000);
  try {
    const r = await fetch(path, {...(body ? {body: JSON.stringify(body)} : {}),
                                signal: ctl.signal});
    const j = await r.json().catch(() => ({error: 'bad response ('+r.status+')'}));
    if (!r.ok && !j.error) j.error = 'HTTP ' + r.status;
    return j;
  } catch (e) {
    return {error: e.name === 'AbortError'
            ? 'Timed out - the server may be busy with Outlook'
            : 'Cannot reach the OrderFlow service (' + e.message + ')'};
  } finally { clearTimeout(t); }
}
```
调用方已经有了 `if (r.error)` 分支，统一返回 `{error}` 形状就能全部生效。
再给 `render()` 加一条"服务不可达"的顶部横幅。

**预期收益**："点了没反应"这类最难排查的反馈问题大幅减少；
端口挪位、COM 卡死时用户能看到原因而不是以为程序死了。

### UX-5　Quick Convert 预览卡：表单即时校验缺失 —— P2

**问题描述**
`qEdit`（编辑行的 code/qty/cost）和 `qShipField`（地址块）都是
**只写状态、不校验、不回显**（`report.py` 对应函数体只有两行）。
用户填完才知道错，要等生成后看文件。而规则其实很清楚：
数量须为正整数、单价须为正数、Sold-To/Ship-To 须为 10 位账号
（`_typed_party` 的清洗规则已经写在 `of_server.py:141`）。

**优化方向**
输入时即时校验并**就地高亮**（红框 + 行内提示），规则与后端共用一套：
```js
function qEdit(i, field, value){
  const v = value.trim();
  const bad = field === 'qty'  ? !/^\d+$/.test(v) && v !== ''
            : field === 'cost' ? !(v === '' || /^\d+(\.\d{1,2})?$/.test(v))
            : false;
  QRESULT.lines[i][field] = v;
  QRESULT.lines[i][field + '_bad'] = bad;   // 渲染时加 class
}
```
配合 Generate 按钮的禁用态：有 `_bad` 行时不允许出文件（而不是生成后才发现）。

**预期收益**：错误左移到输入瞬间，减少"生成→发现→返回→重填"的往返。
与项目"每条修正都要可见"的原则一致。

### UX-6　步骤条回退语义好，但缺"进行中"的可取消性 —— P2

**问题描述**
`stepperHTML`/`stepBack`（`report.py:2325-2360`）设计得不错：
"finished step is a way BACK"、`PREVIEW_SEQ` 防止慢请求回填错误页面。
但预览（`/api/order_preview`，会真的读 PO、调 Claude API）一旦发出，
**用户无法取消**，只能 `stepBack` 然后干等 —— 那次 API 调用照跑、照计费。
`preview_order` 的 docstring 也写明 "It costs one API call"。

3. UI：步骤 2 的"Reading the PO…"卡片加一个 **Cancel** 文字按钮。

**预期收益**：误点/换单时不再浪费一次 API 调用；用户对"正在读"有控制感。
优先级放 P2 是因为要动到服务端的中断语义，不是纯前端。

### UX-7　空状态与首次使用引导参差 —— P2

**问题描述**
不少空状态写得很好（`renderQuick` 的 "No PDF or Excel file in this folder."、
`renderCompleted` 的 "Nothing completed on …"），但也有硬伤：

**预期收益**：新用户首次上手的"这是坏了还是在等"感减少；
对老用户来说，出错时的恢复路径更短。

## 四、2026-10-28 已落地：Inbox 的 Sold-To / Ship-To 加载（PERF-7 / PERF-8）

### 症状

Inbox 出表之后，Sold-To / Ship-To 两列要停一会儿才从占位符变成下拉框；一页 12 家客户时
停顿肉眼可见。以为是对面（服务端）慢，实际是**同一份 2.8 MB 主数据被反复读**。

### 定位（按贡献从大到小）

| # | 问题 | 量级（一页 12 行 / 9 个已知域） |
|---|---|---|
| 1 | `_pairs_by_domain()` 每次调用都重读并重解析 `ship_to_master.json`，再把 7,418 行按域分组；`sold_options()` 和 `ship_options()` **各调一次** → 一次请求解析两遍 | 每次请求 ~75 ms CPU |
| 2 | 前端 `needParty()` **每个域发一个请求**（9 个），全部落在同一个 GIL 上，互相抢 | 8.0 s CPU / 1.57 s 墙钟 |
| 3 | `ship_conflicts()` 每次 `/api/dashboard` 都重读 2.8 MB 再遍历 7,418 行（60 s 轮询、同步期间 3 s 一次） | 每次 ~23 ms |
| 4 | `ship_master.states()` 声称有 mtime 缓存，**实际从未命中**（见上） | 每次 ~17 ms |
| 5 | `patchParty()` 每个域扫一遍 `document.querySelectorAll` → N 次 DOM 遍历 | 12 次 |
| 6 | 占位符是一个「…」，跟"永远填不上"看不出区别 | — |

真正**不是**瓶颈的：网络（本机回环）、JSON 解析、`<option>` 构建（4,699 个 option 的
`innerHTML` 只需 ~21 ms）。所以任何"改前端解决"的方向都是错的。

### 优化（已实施）

1. `_pairs_by_domain()` 按 **`master_key()`（两张主数据表的 mtime+size）+ 目录** 记忆化：
   一次构建，之后 0 成本；任一表被写（上传、改单元格、加行、清空）自动失效。
2. `/api/party_options` 接受 `{domains: [...]}`，**一页一次请求**；单 `domain` 的旧形式保留
   （Quick Convert / Reopen 在用），批量分支就是同样两次调用循环，不会出现两套逻辑。
3. `ship_conflicts` 与 `states()` 同样挂到 `master_key()` 上；`states()` 改用 `_stat_key()`。
4. 前端 `patchParties(domains)` 一次遍历补齐所有单元格。
5. 等待中的单元格换成三点脉冲动画（Uiverse 片段），⚠️ 规则必须收进 `.dots-container .dot`
   ——页面本来就有 `.dot`（9px 状态点），原样照抄会把每个状态点变成 20px 抖动的球。

### 结果（无头 Chrome + 真实服务端，关掉 virtual-time 才准）

| | 请求数 | 首次可用耗时 | 服务端 CPU | dashboard |
|---|---|---|---|---|
| 改前 | 9 | **1,572 ms** | **8,015 ms** | 83 ms |
| 改后 | 1 | **75 ms** | 75 ms | 43 ms |
